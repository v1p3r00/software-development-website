### Q1
LEVEL: junior
TOPIC: CI/CD pipelines
TYPE: theory
QUESTION: A CI pipeline is intended to automatically verify the code for every pull request. Which approach best ensures that faulty code cannot be merged?
A) Run the pipeline only after the production deployment
B) Run the pipeline as part of the pull request validation, and block the merge if required quality or test stages fail
C) Have the developer run the tests locally and manually report the result
D) Run the pipeline only after the merge so that development is not slowed down
ANSWER: B
EXPLANATION: A CI pipeline should provide feedback before the merge, and failed required checks should block the merge. This makes faulty changes visible before they enter the shared branch. Running checks only after production is too late, while relying solely on manual testing is not reproducible and can easily be skipped. Running the pipeline after production is tempting because it makes the pipeline simpler, but it does not prevent faulty code from being merged.
###END
