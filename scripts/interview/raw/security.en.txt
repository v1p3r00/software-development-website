### Q1
LEVEL: junior
TOPIC: Injection
TYPE: theory
QUESTION: In a Java application, the user-provided `username` value is concatenated directly into an SQL query. Which solution directly reduces the risk of SQL injection?
CODE:
ENDCODE
A) HTML-escaping the input
B) Using a parameterized SQL query
C) Switching the database connection to HTTPS
D) Increasing the password field length
ANSWER: B
EXPLANATION: With a parameterized query, the SQL structure and user data are handled as separate parameters, so the input cannot simply become part of the SQL code. HTML escaping can be useful in contexts such as HTML/XSS, but it does not protect against SQL injection. Encrypting the database connection and increasing password length do not prevent SQL query manipulation. HTML escaping is tempting because it can look like a general-purpose "escape input" solution, but each input/output context requires an appropriate security mechanism.

### Q2
LEVEL: junior
TOPIC: XSS
TYPE: output
QUESTION: A web page uses the following code. If the `name` value is `<img src=x onerror=alert(1)>`, what happens?
CODE:
const name = new URLSearchParams(location.search).get("name");
document.getElementById("welcome").innerHTML = "Hello " + name;
ENDCODE
A) The browser automatically converts the `<img>` tag into plain text
B) The CSP will always prevent the event handler from executing
C) The browser can interpret the `<img>` tag as a DOM element, and the `onerror` event can execute JavaScript
D) The code is only dangerous if the `name` value is also stored in the database
ANSWER: C
EXPLANATION: `innerHTML` parses the inserted string as HTML. The `<img src=x>` element can be created, and the failed image load can trigger the `onerror` event, which executes JavaScript. DOM-based XSS does not require a database. A properly configured CSP can reduce the impact of certain XSS payloads, but it is incorrect to assume that every CSP configuration blocks every inline event handler. It is tempting to assume that the browser automatically treats the input as plain text because it originally came from a URL parameter, but `innerHTML` changes the parsing context.
###END

### Q3
LEVEL: junior
TOPIC: Authentication & password storage
TYPE: theory
QUESTION: How should user passwords be stored in a web application?
A) With a strong, modern password-hashing algorithm such as Argon2id, using a unique salt
B) With SHA-256 without a salt
C) With AES-256 using a single key embedded in the application
D) With Base64 encoding
ANSWER: A
EXPLANATION: Passwords should be stored using a dedicated password-hashing algorithm such as Argon2id, with appropriate parameters and a unique salt for each password. The salt prevents identical passwords from producing identical hashes, while the computational cost of the hashing algorithm slows down large-scale offline guessing attempts. SHA-256 is too fast for this purpose, AES is reversible encryption, and Base64 is not a security mechanism at all. SHA-256 is tempting because it is known as a cryptographically strong hash, but password hashing also requires an intentionally high computational cost.
###END

### Q4
LEVEL: junior
TOPIC: CSRF
TYPE: scenario
QUESTION: A traditional session-cookie-based web application automatically sends the cookie with a POST request that performs a bank transfer. Why can this create a CSRF risk?
A) Because cookies are always transmitted without encryption
B) Because POST requests cannot contain session cookies
C) Because CSRF only works against GET requests
D) Because another site can cause the browser to send a request to which the browser automatically adds the session cookie
ANSWER: D
EXPLANATION: CSRF occurs when an attacker-controlled site attempts to cause the victim's browser to send a state-changing request to another origin while the browser may automatically attach the relevant cookies. Possible defenses include CSRF tokens, appropriate `SameSite` cookie settings, and origin checking. Using POST does not by itself provide CSRF protection. It is tempting to consider POST inherently safe because the data is not visible in the URL, but CSRF is not about URL visibility.

### Q5
LEVEL: junior
TOPIC: Sessions & JWT
TYPE: trap
QUESTION: A server issues a JWT access token to a client. Which statement about JWTs is correct?
A) The JWT payload is encrypted by default
B) The JWT signature ensures that the token contents cannot be modified without a valid signature, but it does not by itself hide the payload
C) A JWT can automatically be revoked from every client-side browser
D) Using JWTs eliminates the need for HTTPS
ANSWER: B
EXPLANATION: A typical JWT used as a JWS has a header and payload that are Base64URL-encoded and readable by anyone who possesses the token. The digital signature or MAC provides integrity and authenticity, but not confidentiality. JWT usage does not automatically provide immediate revocation, and TLS is still required to protect the token in transit. It is tempting to think of a JWT as an encrypted token because the token string looks encoded and unreadable, but Base64URL encoding is not encryption.
###END
