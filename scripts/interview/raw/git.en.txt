### Q1
LEVEL: junior
TOPIC: Object model & internals
TYPE: theory
QUESTION: Which statement correctly describes how Git stores content associated with commits?
A) A commit directly contains the complete contents of all files and does not reference other objects.
B) A commit references a tree object, as well as its parent commit(s) and metadata.
C) A commit stores only the diff of the modified files and does not represent the complete filesystem state.
D) A commit stores only a branch name and a timestamp.
ANSWER: B
EXPLANATION: A commit contains, among other things, a reference to a tree object that describes the structure of the filesystem snapshot represented by that commit, as well as references to its parent commit(s) and author/committer metadata. Git's object model is therefore not simply a sequence of diffs stored per commit. The most common incorrect answer is tempting because Git can appear diff-based when using commands such as `log` and `diff`.
###END

### Q2
LEVEL: junior
TOPIC: Staging & commits
TYPE: output
QUESTION: What will the commit contain after the following operations?
CODE:
echo "one" > file.txt
git add file.txt
echo "two" >> file.txt
git commit -m "Add file"
ENDCODE
A) The commit will contain `file.txt` with two lines, "one" and "two".
B) The commit will fail because the file cannot be modified after `git add`.
C) The commit will contain only the "two" line.
D) The commit will contain the version of `file.txt` that was staged, containing only the single line "one".
ANSWER: D
EXPLANATION: `git add` stages the file's contents as they exist at that point in time. The later modification is made in the working tree and is not automatically added to the staging area. Therefore, the commit records the one-line version containing `one`. The most common incorrect answer is tempting because people often think of staging as a continuous state attached to a file rather than a snapshot of its contents at a specific point in time.
###END

### Q3
LEVEL: junior
TOPIC: Branching
TYPE: behavior
QUESTION: In a Git repository, the `main` branch currently points to the end of the `A-B-C` commit chain. You create the `feature` branch at commit `C`, then create a new commit on the feature branch. What happens to the `main` branch?
A) `main` automatically moves to the new feature commit.
B) `main` and `feature` are automatically merged.
C) `main` continues to point to commit `C`.
D) Git creates a new common commit for the two branches.
ANSWER: C
EXPLANATION: In Git, a branch is essentially a movable reference to a commit. After creating `feature`, its reference can move to the new commit, but the `main` reference does not change as a result. The most common incorrect answer is tempting because people often think of a branch as a separate copy rather than as a reference pointing to a commit.

### Q4
LEVEL: junior
TOPIC: Merging & conflicts
TYPE: scenario
QUESTION: Both the `main` and `feature` branches started from the same commit `C`. Each branch has exactly one additional commit, and they modify different files. What does `git merge feature` do by default when you are on the `main` branch?
A) A merge conflict always occurs because both branches contain new commits.
B) Git deletes the feature commit and keeps only the state of `main`.
C) Git automatically squashes the two commits into a single commit.
D) Git creates a merge commit with two parents.
ANSWER: D
EXPLANATION: Because both branches diverged from their common ancestor and neither branch is an ancestor of the other, a fast-forward is not possible. Git therefore creates a merge commit by default, provided there are no conflicts and the merge is not otherwise configured. The merge commit has two parents. The most common incorrect answer is tempting because people often assume that any divergence between branches necessarily causes a conflict.
###END

### Q5
LEVEL: junior
TOPIC: Remotes, fetch, pull & push
TYPE: theory
QUESTION: What is the most important difference between `git fetch origin` and `git pull origin main` under normal circumstances?
A) Fetch updates remote-tracking references without automatically integrating the changes into the current branch, while pull also performs an integration step after fetching.
B) Fetch downloads only tags, while pull downloads only branches.
C) Fetch modifies the working tree, while pull never modifies it.
D) The two commands are completely identical and are simply different names for the same operation.
ANSWER: A
EXPLANATION: `git fetch` downloads new objects from the remote repository and updates remote-tracking references such as `origin/main`, but does not automatically merge or rebase the current branch. `git pull` is essentially a fetch followed by an integration step, which may be a merge or rebase depending on configuration and options. The most common incorrect answer is tempting because both commands involve network communication in everyday Git usage.
###END

### Q6
LEVEL: junior
TOPIC: Undoing changes (reset, revert, restore)
TYPE: trap
QUESTION: You have a published commit on the `main` branch that contains an incorrect change. Other developers have already fetched it. Which approach is generally the most appropriate if you want to avoid rewriting shared history?
A) `git reset --hard HEAD~1` followed by a force push
B) `git restore --source HEAD~1 --staged --worktree .`
C) `git revert HEAD`
D) Delete the `.git` directory and initialize a new repository
ANSWER: C
EXPLANATION: `git revert HEAD` creates a new commit that reverses the changes introduced by the selected commit, preserving the published history. In contrast, `reset --hard` can move the branch reference and working tree backward, which can lead to history rewriting on a shared branch if followed by a force push. The most common incorrect answer is tempting because reset visibly moves the branch back to an earlier state.
###END

QUESTION: You want to find a previous state of a local branch after moving the branch pointer. Which command can you use to view previous ref values for that branch?
A) `git reflog show <branch>`
B) `git remote show <branch>`
C) `git branch --history <branch>`
D) `git log --refs-only <branch>`
ANSWER: A
EXPLANATION: `git reflog show <branch>` displays previous values of the specified branch ref, which can be used to recover a state from before a reset or rebase, for example. The reflog is a local mechanism, and retention of entries depends on configuration and garbage collection. The tempting assumption is that normal `git log` preserves every previous branch pointer, while it primarily displays the commit graph history.

### Q193
LEVEL: senior
TOPIC: Object model & internals
TYPE: theory
QUESTION: Which statement correctly describes the fundamental principle of Git object identification?
A) An object's identifier depends exclusively on the filename.
B) A commit SHA is derived only from the commit message.
C) Git generates a random, permanent identifier for every object.
D) The object identifier is derived from a hash associated with the object's type, size, and content.
ANSWER: D
EXPLANATION: Git uses content-addressed object storage: the object identifier is derived from a hash based on the appropriate object type, size, and content. As a result, identical content of the same object type can produce the same object identifier. The tempting assumption is that Git assigns random IDs like a traditional database, while Git's object identification is content-based.
###END

QUESTION: In a very large repository, managing the Git index introduces significant performance overhead. Which Git feature specifically aims to reduce the cost of rewriting the index?
A) Shallow clone
B) Split index
C) Annotated tag
D) Reflog expiration
ANSWER: B
EXPLANATION: Split index allows relatively unchanged portions of the index to remain in a shared base index while changes are stored in a smaller split index. This can reduce index management costs, particularly in repositories with very large numbers of tracked files. The tempting shallow clone reduces the depth of repository history but does not target the cost of rewriting the index.

B) `git merge --squash-only`

### Q198

QUESTION: After running `git reset --hard`, you realize that you need the branch tip from before the reset, and you found the correct commit in the reflog. What is the safer first step for preserving the recovered state?
A) Immediately run `git gc --prune=now`.

C) Delete the reflog so there are no more old states.
D) Run another `git reset --hard` to an arbitrary commit.
ANSWER: B

The tempting cleanup approaches may seem useful because they relate to Git object management, but the immediate goal here is to preserve the recovered commit.

### Q199
LEVEL: senior
TOPIC: History, log, blame & bisect
TYPE: algorithm
QUESTION: You are investigating a regression in a history containing thousands of commits. Why is the fundamental approach used by `git bisect` efficient?
A) It tests every commit sequentially in chronological order.
B) It examines only merge commits.
C) It repeatedly reduces the search range to approximately half based on a known good and a known bad state.
D) It searches commit messages for keywords related to the bug.
ANSWER: C
EXPLANATION: `git bisect` uses a binary-search strategy: it tests commits between a known good and a known bad revision, then discards one half of the search range based on the result. This means that far fewer tests are required for a large number of commits than with a linear search. The tempting assumption is that bisect analyzes commit messages, but it uses the behavior of revisions to guide the search.
###END

### Q200
LEVEL: senior
TOPIC: Submodules & monorepos
TYPE: production
QUESTION: A CI pipeline wants to download and check out as little as possible from a large monorepo, because it only needs files belonging to a single component. Which combination can help achieve this?
A) Use `git sparse-checkout` together with a partial clone.
B) Use only `git clean -fd` after a full clone.
C) Use only annotated tags.
D) Create a separate stash for every component.
ANSWER: A
EXPLANATION: Sparse-checkout limits which paths are materialized in the working tree, while partial clone can avoid downloading certain Git objects until they are needed. Together they can significantly reduce the initial cost of a suitable monorepo CI workflow. The tempting `git clean` approach may seem useful because it removes files from the working tree, but it does not reduce the Git objects that have already been downloaded.
###END
