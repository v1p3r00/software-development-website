### Q1
LEVEL: junior
TOPIC: Object model & internals
TYPE: theory
QUESTION: Melyik állítás írja le helyesen, hogyan tárolja a Git a commitokhoz tartozó tartalmat?
A) A commit közvetlenül az összes fájl teljes tartalmát tartalmazza, és nem hivatkozik más objektumokra.
B) A commit egy tree objektumra, valamint a szülő commit(ok)ra és metaadatokra hivatkozik.
C) A commit kizárólag a módosított fájlok diffjét tárolja, a teljes fájlrendszer-állapotot nem.
D) A commit csak egy branch nevét és egy időbélyeget tárol.
ANSWER: B
EXPLANATION: A commit objektum többek között egy tree objektumra hivatkozik, amely az adott commit fájlrendszer-pillanatképének szerkezetét írja le, továbbá tartalmazza a szülő commit(ok) azonosítóját és a szerzői/commit metaadatokat. A Git objektummodellje ezért nem egyszerűen commitonként eltárolt diffek sorozata. A leggyakoribb téves válasz azért csábító, mert a Git diff-alapú működésűnek tűnik a felhasználói parancsok, például a log és diff alapján.
###END

### Q2
LEVEL: junior
TOPIC: Staging & commits
TYPE: output
QUESTION: Mit fog tartalmazni a commit az alábbi műveletek után?
CODE:
echo "one" > file.txt
git add file.txt
echo "two" >> file.txt
git commit -m "Add file"
ENDCODE
A) A commitban a file.txt két soros, "one" és "two" tartalommal lesz.
B) A commit sikertelen lesz, mert a fájlt a git add után már nem lehet módosítani.
C) A commit csak a "two" sort tartalmazza.
D) A commit a staging területre került, egy soros "one" tartalmú verziót tartalmazza.
ANSWER: D
EXPLANATION: A `git add` az adott pillanatban a fájl tartalmát a staging area-ba helyezi. A későbbi módosítás a working tree-ben történik, és automatikusan nem kerül bele a staging area-ba. Ezért a commit az `one` tartalmú, egy soros állapotot rögzíti. A leggyakoribb rossz válasz azért csábító, mert sokan úgy gondolják, hogy a staging egy fájlhoz kötött folyamatos állapot, nem pedig egy adott tartalom pillanatfelvétele.
###END

### Q3
LEVEL: junior
TOPIC: Branching
TYPE: behavior
QUESTION: Egy Git repositoryban a `main` branch jelenleg a `A-B-C` commitlánc végén áll. Létrehozod a `feature` branchet a `C` commitnál, majd készítesz egy új commitot a feature branchen. Mi történik a `main` branch-csel?
A) A `main` automatikusan az új feature commitra lép.
B) A `main` és a `feature` automatikusan merge-elődik.
C) A `main` változatlanul a `C` commitra mutat.
D) A Git új közös commitot hoz létre a két branch számára.
ANSWER: C
EXPLANATION: A branch Gitben alapvetően egy commitra mutató mozgatható referencia. A `feature` létrehozása után annak referenciája továbbmozoghat az új commitra, de a `main` referencia ettől nem változik. A leggyakoribb téves válasz azért csábító, mert a branch létrehozását egyes fejlesztők különálló példányként képzelik el, nem pedig egy commitra mutató referenciaként.
###END

### Q4
LEVEL: junior
TOPIC: Merging & conflicts
TYPE: scenario
QUESTION: A `main` és a `feature` branch is a közös `C` commitból indult. Mindkettőn pontosan egy-egy új commit készült, és különböző fájlokat módosítottak. Mit tesz alapértelmezés szerint a `git merge feature`, ha a `main` branchen állsz?
A) Mindig merge conflict keletkezik, mert mindkét branch új commitot tartalmaz.
B) A Git törli a feature commitot, és csak a main állapotát tartja meg.
C) A Git automatikusan squasholja a két commitot egyetlen commitba.
D) A Git egy merge commitot hoz létre, amelynek két szülője van.
ANSWER: D
EXPLANATION: Mivel mindkét branch eltért a közös őstől, és nincs fast-forward lehetőség, a Git alapértelmezésben merge commitot hoz létre, feltéve hogy nincs konfliktus és a merge nincs másképp konfigurálva. A merge commit két szülőre hivatkozik. A leggyakoribb rossz válasz azért csábító, mert a konfliktust sokan az ágak közötti bármilyen eltérés kötelező következményének tekintik.
###END

### Q5
LEVEL: junior
TOPIC: Remotes, fetch, pull & push
TYPE: theory
QUESTION: Mi a legfontosabb különbség a `git fetch origin` és a `git pull origin main` között normál esetben?
A) A fetch frissíti a távoli referenciákat anélkül, hogy a jelenlegi branch munkafájába automatikusan beolvasná a változásokat, míg a pull fetch után integrációt is végez.
B) A fetch csak tageket tölt le, a pull pedig csak brancheket.
C) A fetch módosítja a working tree-t, a pull pedig soha nem módosítja.
D) A két parancs teljesen azonos, csak más néven érhetők el.
ANSWER: A
EXPLANATION: A `git fetch` lekéri a távoli repository új objektumait és frissíti a remote-tracking referenciákat, például az `origin/main` állapotát, de nem merge-öli vagy rebase-eli automatikusan a jelenlegi branch-et. A `git pull` lényegében fetch és azt követő integráció, amely a konfigurációtól függően merge vagy rebase lehet. A leggyakoribb téves válasz azért csábító, mert mindkét parancs hálózati műveletként jelenik meg a mindennapi használatban.
###END

### Q6
LEVEL: junior
TOPIC: Undoing changes (reset, revert, restore)
TYPE: trap
QUESTION: Van egy már publikált commitod a `main` branchen, amely hibás változtatást tartalmaz. A commitot más fejlesztők is letöltötték. Melyik megoldás a leginkább megfelelő, ha az előzmények átírását szeretnéd elkerülni?
A) `git reset --hard HEAD~1` majd force push
B) `git restore --source HEAD~1 --staged --worktree .`
C) `git revert HEAD`
D) A `.git` könyvtár törlése és új repository inicializálása
ANSWER: C
EXPLANATION: A `git revert HEAD` egy új commitot hoz létre, amely visszafordítja a kiválasztott commit változtatásait, így a már publikált history érintetlenül megmarad. A `reset --hard` ezzel szemben a branch referenciáját és a munkakönyvtárat is visszaállíthatja, ami megosztott branchen history-átíráshoz vezethet. A leggyakoribb rossz válasz azért csábító, mert a reset közvetlenül láthatóan visszaviszi a branch-et a korábbi állapotra.
###END

A leggyakoribb rossz válasz azért csábító, mert a stash ideiglenes tárolóként működik, és könnyű összekeverni egy ideiglenes commit vagy branch fogalmával.

### Q8
LEVEL: junior
TOPIC: Cherry-pick
TYPE: output
QUESTION: Egy branch-en lévő egyetlen commit módosítja a `config.txt` fájlt. Egy másik branch-en állsz, és kiadod a `git cherry-pick <commit>` parancsot konfliktus nélkül. Mi történik?
A) A Git átmozgatja az eredeti commitot az aktuális branch-re, így az eredeti branch elveszíti.
B) A Git csak a commit üzenetét másolja át, a fájlváltozásokat nem.
C) A Git az eredeti commit objektumot új szülővel módosítja.
D) A Git az adott commit változtatásait alkalmazza az aktuális branch-en, és új commitot hoz létre.

A kiválasztott commit változtatásait alkalmazza az aktuális HEAD-re, majd ebből rendszerint új commit jön létre, amelynek más lehet a commitazonosítója és a szülője. A leggyakoribb téves válasz azért csábító, mert a parancs úgy tűnik, mintha egy meglévő commitot "átvinne" egyik branchből a másikba.
###END
