### Q1
LEVEL: junior
TOPIC: CI/CD pipelines
TYPE: theory
QUESTION: Egy CI pipeline célja, hogy minden pull request esetén automatikusan ellenőrizze a kódot. Melyik megközelítés biztosítja legjobban, hogy hibás kód ne jusson el a merge-ig?
A) A pipeline csak a production deploy után fusson le
B) A pipeline fusson le a pull request ellenőrzésekor, és sikertelen quality/test stage esetén blokkolja a merge-t
C) A fejlesztő manuálisan futtassa lokálisan a teszteket, majd jelezze az eredményt
D) A pipeline csak a merge után fusson, hogy ne lassítsa a fejlesztést
ANSWER: B
EXPLANATION: A CI pipeline-nak a merge előtt kell visszajelzést adnia, és a kötelező ellenőrzések sikertelensége esetén célszerű blokkolni a merge-et. Így a hibás változtatás már a közös branch-be kerülés előtt láthatóvá válik. A production utáni ellenőrzés túl késői, a kizárólag manuális tesztelés pedig nem reprodukálható és könnyen kimarad. A production deploy utáni futtatás azért csábító, mert egyszerűbbnek tűnik a pipeline, de nem akadályozza meg a hibás kód bekerülését.
###END

### Q3

TYPE: output
QUESTION: Melyik Dockerfile-részlet eredményez kisebb és általában biztonságosabb runtime image-et egy Node.js alkalmazás számára?
A)
CODE:
FROM node:22
COPY . /app
WORKDIR /app
RUN npm install
CMD ["npm", "start"]
ENDCODE
B)
CODE:
FROM ubuntu:latest
RUN apt-get update && apt-get install -y nodejs npm
COPY . /app
WORKDIR /app
RUN npm install
CMD ["npm", "start"]
ENDCODE
C)
CODE:
FROM node:22
USER root
COPY . /app
WORKDIR /app
RUN npm install
CMD ["npm", "start"]
ENDCODE
D)
CODE:
FROM node:22-alpine
WORKDIR /app
