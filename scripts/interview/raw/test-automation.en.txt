### Q1
LEVEL: junior
TOPIC: Test strategy & pyramid
TYPE: theory
QUESTION: You are designing a testing strategy for a new web application. Which approach best aligns with the classic test pyramid?
A) Many fast unit tests, fewer API/integration tests, and even fewer slow UI end-to-end tests
B) Few unit tests and many UI end-to-end tests because they validate real user behavior
C) Only end-to-end tests, so there is no need to deal with internal implementation details
D) The same number of tests at every layer to ensure balanced coverage
ANSWER: A
EXPLANATION: The test pyramid principle is to have the largest number of cheap, fast, and isolated tests, with fewer expensive and slow UI end-to-end tests. This provides faster feedback and generally results in a more stable test suite. Having many UI tests can be tempting because they are closest to real user workflows, but they are typically slower and more fragile.
###END

TOPIC: Unit testing

CODE:
@Test

    Calculator calculator = new Calculator();

    int result = calculator.add(2, 3);

    assertEquals(5, result);
}
ENDCODE
A) The test passes because the result is 5
B) The test fails because `assertEquals` cannot be used with primitive `int` values
C) The test only passes if `Calculator` is a Spring bean

ANSWER: A
EXPLANATION: The `Calculator` is instantiated directly, `add(2, 3)` returns 5, and therefore the expected and actual values match. The need for a Spring bean can be tempting to assume because many Java projects use JUnit together with Spring, but a simple unit test does not require Spring.
